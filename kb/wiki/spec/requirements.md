# JinMac 맥 작업 부하 검진 앱: 개발 요구사항

> Sources: 요구사항 초안 (2026-09-17, @Someone)
> Raw: [2026-09-17-requirements-draft.md](../../raw/references/2026-09-17-requirements-draft.md)

맥에서 하는 실제 작업을 1\~2주 동안 측정하고, 자원별로 여유·경계·한계를 판정해 다음 기기 구매의
근거가 되는 한국어 리포트를 만드는 앱의 요구사항이다.

1장부터 13장까지는 원문 그대로 옮겼다. 프로젝트 뼈대를 만들면서 내린 결정과, 원문을 macOS의
실제 API와 대조해 찾은 검토 의견은 14장에 적었다. 검토 의견을 채택하면 해당 본문 절을 고치고
14장에서 상태를 바꾼다.

---

## 1. 개요와 목적

이 앱은 "지금 내가 하는 작업을 이 맥이 잘 소화하고 있는가"라는 질문에 측정 데이터로 답한다. 상시 모니터가 아니라 검진 도구다. 설치 후 1\~2주 동안 백그라운드에서 사용량을 기록하고, 기록이 끝나면 한국어 "작업 부하 프로파일 리포트"를 한 번 생성한다.

기존 모니터링 앱(iStat Menus, Stats, TG Pro)은 숫자를 보여주는 데서 끝나고, MacPulse는 스로틀링·배터리 같은 이벤트를 설명한다. 이 앱의 차별점은 사용자의 실제 워크로드와 기기의 궁합을 자원별로 판정하고, 다음 기기 구매 결정에 쓸 수 있는 근거를 남기는 것이다.

리포트가 답하는 세 가지:

- 지난 기간 동안 어느 자원(RAM, CPU, GPU, 디스크, 열)이 얼마나 자주 한계에 닿았는가
- 그때 어떤 작업(포그라운드 앱)을 하고 있었는가
- 다음 맥을 산다면 어느 항목을 올리고 어느 항목은 유지해도 되는가

## 2. 핵심 원칙과 제약

운영 비용 0원, 데이터 외부 전송 0건, 애플 개발자 등록 없음이 설계 전체를 규정한다.

| 제약 | 요구사항 |
| --- | --- |
| 비용 | 서버, 클라우드 API, 유료 SDK, 유료 인증서를 일절 쓰지 않는다. Apple Developer Program($99/년)도 가입하지 않는다. |
| 로컬 전용 | 수집·저장·분석·리포트 생성이 모두 사용자 기기 안에서 끝난다. 앱은 네트워크 요청을 하지 않는다(업데이트 확인 제외). |
| 해석 | 판정은 결정론적 규칙 엔진이 내리고, 온디바이스 AI는 판정 결과를 한국어 문장으로 다듬는 데만 쓴다. AI가 판정을 바꾸거나 수치를 만들어내지 않는다. |
| 배포 | GitHub Releases로 직배포. App Store, 공증(notarization), Developer ID 서명 없음. |
| 수익 | 무료. 광고, 인앱 결제, 텔레메트리 없음. |
| 근거 우선 | 모든 판정 문장은 근거 수치(발생 시간 비율, 발생 횟수, 당시 앱)를 함께 표시한다. 근거 없는 권고는 출력하지 않는다. |

## 3. 대상 사용자와 사용 시나리오

1차 사용자는 다음 맥 구매를 앞두고 "지금 기기로 충분한가, 어디를 올려야 하나"를 고민하는 맥 사용자다. 커뮤니티에서 "이 작업에 이 스펙이면 되나요"라고 묻는 사람이 바로 이 사용자다.

| 시나리오 | 사용자 행동 | 앱이 하는 일 |
| --- | --- | --- |
| 구매 전 검진 | 설치 후 평소처럼 1\~2주 사용 | 백그라운드 기록 → 종료 시 리포트 생성 |
| 특정 작업 점검 | 영상 편집·빌드 같은 작업 전에 "세션 시작" 클릭, 끝나면 "세션 종료" | 그 구간만 1초 간격 고해상도 기록 → 세션 리포트 |
| 커뮤니티 공유 | 리포트 카드(PNG)를 내보내 게시글에 첨부 | 표준 형식 카드 + JSON 생성 |
| 재검진 | 새 맥으로 바꾼 뒤 같은 기간 다시 기록 | 이전 리포트와 비교 |

사용자는 기술 용어를 몰라도 리포트를 읽을 수 있어야 한다. "메모리 압박", "스왑" 같은 용어는 리포트 안에서 한 줄 설명과 함께 쓴다.

## 4. 기능 요구사항

기능은 수집 → 태깅 → 판정 → 리포트 → 내보내기의 다섯 단계로 나뉜다. 각 항목 앞의 코드(F-xx)는 이슈 추적용 식별자다.

### 4.1 수집 (Collector)

| 코드 | 요구사항 | 비고 |
| --- | --- | --- |
| F-01 | 기본 5초 간격(설정 가능 1\~30초)으로 아래 지표를 샘플링한다 | 검진 기간 기본 14일, 사용자가 7/14/30일 중 선택 |
| F-02 | 메모리: 총량, 사용량, 압축 메모리, 스왑 사용량, 스왑 in/out 누적, macOS 메모리 압박 등급(정상/경고/위험) | `host_statistics64`, `sysctl vm.swapusage`, 압박 등급은 샘플마다 `sysctl kern.memorystatus_vm_pressure_level` (14.2a 참조) |
| F-03 | CPU: 전체 사용률, P코어/E코어 별 사용률, 현재 주파수 | `host_processor_info`, IOReport(주파수) |
| F-04 | GPU: 사용률, 사용 메모리 | IOKit `AGXAccelerator` 통계 |
| F-05 | 디스크: 읽기/쓰기 처리량, I/O 대기 비율, 남은 용량 비율 | IOKit 블록 스토리지 통계 |
| F-06 | 열: CPU/GPU 온도, 팬 RPM, 스로틀링 상태 | SMC(IOHIDFamily on Apple Silicon). 읽기 실패 시 항목 비활성화하고 계속 진행 |
| F-07 | 전력: 배터리 여부, 전원 연결 여부 | 배터리 모드 여부는 판정 가중치에 반영 |
| F-08 | 컨텍스트: 매 샘플마다 포그라운드 앱 번들 ID, 화면 잠금/유휴 여부 | `NSWorkspace.frontmostApplication`, `CGEventSource` 유휴 시간 |
| F-09 | 샘플마다 상위 CPU/메모리 프로세스 5개의 이름과 사용량 | 사용자 데이터(파일명, 창 제목)는 수집하지 않는다 |
| F-10 | 수집기 자체 CPU 사용률 평균 1% 미만, 상주 메모리 50MB 미만 | 측정 도구가 부하를 만들지 않아야 한다 |
| F-11 | 잠자기·재부팅 후 자동 재개. 로그인 항목 등록은 사용자 동의 후. 실행할 때마다 등록 상태를 확인하고, 풀려 있으면 메뉴에 알린다 | `SMAppService.mainApp`. 등록은 코드 서명에 묶이므로 배포본은 자체 서명 인증서로 서명한다 (10.1절, 14.5a 참조) |

### 4.2 워크로드 태깅

| 코드 | 요구사항 |
| --- | --- |
| F-20 | 포그라운드 앱 번들 ID를 내장 매핑 테이블로 워크로드 카테고리에 자동 분류한다: 영상 편집, 사진·디자인, 개발(IDE·컴파일), 3D·렌더링, 음악 제작, 가상머신·컨테이너, 브라우징·문서, 게임, AI·머신러닝, 기타 |
| F-21 | 매핑 테이블은 앱 안에 JSON으로 번들하고, 사용자가 카테고리를 직접 고쳐 쓸 수 있다 |
| F-22 | 수동 세션: 메뉴바에서 "세션 시작/종료"로 구간을 지정하면 그 구간은 1초 간격으로 기록하고 이름을 붙인다 |
| F-23 | 유휴 상태(입력 없음 5분 이상, 화면 잠금)는 판정 모수에서 제외한다. 다만 그동안에도 CPU 전체 사용률이나 GPU 사용률이 기준(초기값 50%, 번들 JSON) 이상이면 `무인 작업`으로 분류해 모수에 남긴다(14.2f 참조). 백그라운드 부하(인덱싱, 백업)는 별도 항목으로 표시한다 |

### 4.3 규칙 엔진

| 코드 | 요구사항 |
| --- | --- |
| F-30 | 검진 기간 종료 시(또는 사용자 요청 시) 저장된 샘플로 자원별 판정을 계산한다. 판정 기준은 5장 참조 |
| F-31 | 판정 결과는 자원별 등급(여유/경계/한계) + 근거 수치 + 발생 시 상위 워크로드 3개 + 발생 시 상위 프로세스 3개로 구성된다 |
| F-32 | 규칙과 임계값은 코드가 아닌 번들 JSON에 두어 앱 업데이트 없이 조정 가능하게 한다 |
| F-33 | 같은 입력에는 항상 같은 출력을 낸다(결정론적). 단위 테스트로 보장 |
| F-34 | 데이터가 판정에 충분하지 않으면(활성 시간 10시간 미만) 등급 대신 "판정 보류"를 내고 이유를 표시한다 |

### 4.4 리포트 생성

| 코드 | 요구사항 |
| --- | --- |
| F-40 | 리포트는 한국어로 생성한다. 구성: 요약 한 문단 → 자원별 판정 카드 → 워크로드별 분석 → 구매 참고 → 근거 데이터 |
| F-41 | 요약과 자원별 설명 문장은 온디바이스 AI(6장)가 규칙 엔진 결과만 입력받아 작성한다. AI 사용 불가 시 템플릿 문장으로 대체하며 사용자는 차이를 느끼지 않아야 한다 |
| F-42 | 구매 참고 항목은 "이 항목을 올리면 체감 개선이 클 것", "이 항목은 현 수준 유지 가능"의 두 목록으로 제시한다. 구체적 모델명·가격은 제시하지 않는다 |
| F-43 | 근거 데이터 섹션에는 메모리 압박 등급 시간 분포, P코어 포화 시간, 스로틀링 횟수·지속 시간을 Swift Charts로 그린다 |
| F-44 | 리포트는 앱 안에서 열람하고, 과거 리포트를 목록으로 보관한다 |

### 4.5 내보내기와 공유

## 5. 규칙 엔진 판정 기준 (초안)

판정 모수는 유휴를 뺀 활성 시간이며, 각 자원은 "한계 신호가 활성 시간 중 차지한 비율"로 등급을 정한다. 아래 임계값은 초기값이고, 번들 JSON(F-32)에서 조정한다.

| 자원 | 한계 신호 정의 | 여유 | 경계 | 한계 |
| --- | --- | --- | --- | --- |
| 메모리 | 메모리 압박 "경고" 이상, 또는 스왑 아웃 증가율 > 초당 1MB. 스왑 사용량은 근거 수치로만 쓴다(14.3a 참조) | < 5% | 5\~20% | > 20% |
| 메모리(강) | 메모리 압박 "위험" | 0% | < 2% | ≥ 2% |
| CPU | P코어 평균 사용률 ≥ 90%가 30초 이상 지속 | < 10% | 10\~30% | > 30% |
| GPU | GPU 사용률 ≥ 90%가 30초 이상 지속 | < 10% | 10\~30% | > 30% |
| 열 | 스로틀링(주파수가 정격 대비 20% 이상 하락 & 온도 상승) | 0회 | 주 1\~3회 | 주 4회 이상 또는 1회 10분 이상 |
| 디스크 | I/O 대기 ≥ 30%가 30초 이상, 또는 남은 용량 < 15% | < 5% | 5\~15% | > 15% 또는 용량 부족 |

판정 보조 규칙:

- CPU가 "한계"라도 그때 워크로드가 렌더링·컴파일·내보내기처럼 본래 풀부하를 쓰는 작업이면 "의도된 풀부하"로 표기하고 등급을 한 단계 낮춘다. 풀부하 자체는 병목이 아니라 정상 동작이다.
- 메모리 "한계"와 디스크 I/O 대기가 같은 시간대에 겹치면 "스왑으로 인한 디스크 부하"로 묶어 메모리 항목으로 귀속시킨다.
- 배터리 모드에서만 발생한 CPU·열 신호는 별도 표기하고 전원 연결 시 데이터로 다시 판정한다.
- 강한 메모리 신호("메모리(강)")가 한계면 다른 항목과 무관하게 종합 판정을 "한계"로 둔다. RAM은 Apple Silicon에서 구매 후 늘릴 수 없는 유일한 자원이라 가장 보수적으로 본다.
- 종합 판정은 자원별 등급 중 가장 나쁜 것을 따르되, 근거 문장에는 어느 자원 때문인지 명시한다.

구매 참고 매핑(F-42):

| 판정 | 구매 참고 문구(요지) |
| --- | --- |
| 메모리 한계 | 다음 기기에서 RAM 한 단계 상향을 최우선으로 |
| 메모리 경계 | 현재 용량은 가능하나 작업이 늘 예정이면 상향 고려 |
| CPU 한계 (의도된 풀부하 아님) | 코어 수가 많은 칩 등급 상향 |
| CPU 한계 (의도된 풀부하) | 칩 상향 시 해당 작업 시간이 줄어들지만 필수는 아님 |
| GPU 한계 | GPU 코어 수가 많은 칩 등급 상향 |
| 열 한계 | 팬이 있는 폼팩터(MacBook Pro, Mac mini, Mac Studio) 고려 |
| 디스크 용량 부족 | 저장 용량 상향 또는 외장 SSD |

## 6. 온디바이스 AI 요구사항

AI는 Apple의 Foundation Models 프레임워크(macOS 26 이상, Apple Intelligence 활성화 필요)를 쓰고, 역할은 규칙 엔진 결과를 한국어 문장으로 다듬는 것으로 제한한다.

| 코드 | 요구사항 |
| --- | --- |
| A-01 | `SystemLanguageModel.default.availability`로 사용 가능 여부를 확인하고, 불가 사유(기기 미지원, Apple Intelligence 꺼짐, 모델 다운로드 중)를 설정 화면에 표시한다 |
| A-02 | 입력은 규칙 엔진의 구조화 결과(자원별 등급, 근거 수치, 상위 워크로드·프로세스)만 넘긴다. 원시 샘플, 프로세스 전체 목록, 파일 경로는 넘기지 않는다 |
| A-03 | 출력은 `@Generable` 구조체로 받는다: 요약(3문장 이내), 자원별 설명(각 2문장 이내), 구매 참고 문장. 자유 텍스트를 그대로 리포트에 쓰지 않는다 |
| A-04 | 프롬프트에 등급과 수치를 바꾸지 말라는 지시를 넣고, 생성 후 검증 단계에서 입력 수치가 출력에 그대로 있는지 확인한다. 불일치 시 템플릿 문장으로 대체 |
| A-05 | 컨텍스트 한계(약 4천 토큰)를 고려해 자원 항목별로 나눠 호출한다. 리포트 1건당 호출 6회 이내 |
| A-06 | 생성 시간 목표 10초 이내(M1 기준). 초과 시 템플릿 리포트를 먼저 보여주고 AI 문장을 나중에 채운다 |
| A-07 | Foundation Models 불가 시 폴백은 템플릿 문장이다. 폴백 여부는 리포트 하단에 한 줄로 표기한다 |
| A-08 | llama.cpp·MLX 등 모델 내장 방식은 채택하지 않는다. 앱 용량과 발열 때문에 "측정 도구가 부하를 만드는" 문제가 생긴다 |
| A-09 | 사용자 본인 API 키 입력 기능은 1차 범위에서 제외한다(비용·네트워크 0 원칙 유지) |

프롬프트 설계 원칙: 문체는 존댓말 설명문, 단정 대신 근거 인용("\~한 시간이 전체의 23%였습니다"), 과장 어휘 금지, 모델명·가격 언급 금지.

## 7. 데이터 모델과 저장

모든 데이터는 `~/Library/Application Support/<앱이름>/` 아래 SQLite 파일 하나에 저장하고, 앱 삭제 안내에 이 경로를 명시한다.

| 테이블 | 주요 컬럼 | 비고 |
| --- | --- | --- |
| `sample` | ts, mem\_used, mem\_compressed, swap\_used, swap\_in, swap\_out, mem\_pressure(0/1/2), cpu\_total, cpu\_p, cpu\_e, cpu\_freq, gpu\_util, gpu\_mem, disk\_read, disk\_write, io\_wait, temp\_cpu, temp\_gpu, fan\_rpm, throttled(bool), on\_battery(bool), idle(bool), front\_app | 5초 간격, 14일 ≈ 24만 행, 약 40MB |
| `top_process` | sample\_ts, name, cpu, mem | 샘플당 5행 |
| `session` | id, name, started\_at, ended\_at, interval\_sec | 수동 세션 메타 |
| `session_sample` | session\_id + `sample`과 동일 컬럼 | 1초 간격 |
| `checkup` | id, started\_at, ended\_at, target\_days, status | 검진 1회 = 1행 |
| `report` | id, checkup\_id, created\_at, verdict\_json, text\_json, schema\_version | 판정 결과와 문장을 분리 저장 |
| `app_category` | bundle\_id, category, user\_overridden | 내장 매핑 + 사용자 수정 |

- 검진 종료 후 원시 `sample`은 리포트 생성이 끝나면 요약(시간별 집계)으로 축약하고 원본은 30일 뒤 삭제한다. 사용자가 CSV로 보관할 수 있다.
- 리포트 JSON 스키마는 `schema_version`을 두어 비교 기능(F-52)에서 호환성을 검사한다.
- 저장 파일은 암호화하지 않는다(외부 전송이 없고, 내용에 사용자 파일 정보가 없음).

## 10. 배포

GitHub Releases로 zip을 직배포하되, 개발자 등록이 없으므로 Gatekeeper 경고를 사용자가 스스로 넘기게 안내하는 것이 배포의 핵심 과제다.

### 10.1 개발자 미등록이 만드는 제약

| 제약 | 영향 | 대응 |
| --- | --- | --- |
| Developer ID 서명·공증 불가 | 처음 실행 시 "확인되지 않은 개발자" 경고. macOS 15부터는 우클릭 → 열기 우회가 사라져 시스템 설정 → 개인정보 보호 및 보안 → "그래도 열기"를 눌러야 한다 | README와 릴리즈 노트에 스크린샷 포함 설치 가이드. 터미널 대안 `xattr -d com.apple.quarantine <앱경로>`도 함께 안내 |
| 서명 없음 = 앱 무결성 보장 없음 | 배포 파일 변조 여부를 사용자가 확인할 수 없음 | 릴리즈마다 SHA-256 체크섬 게시. 서명은 반드시 적용(미서명 바이너리는 Apple Silicon에서 실행 자체가 거부됨). 배포본은 자체 서명 인증서(`JinMac Self-Signed`)로 서명해 지정 요구사항을 버전 사이에 고정하고, 인증서가 없는 개발 빌드는 ad-hoc 서명(`codesign -s -`)을 쓴다. 인증서는 Gatekeeper 경고를 없애지 못한다(14.5a 참조) |
| iCloud, 푸시, App Groups 등 유료 계정 전용 기능 불가 | 이 앱은 해당 기능을 쓰지 않음 | 영향 없음 |
| App Store 배포 불가 | 검색 노출 없음 | 커뮤니티(맥쓰사 등)와 GitHub가 유일한 유통 경로. 리포트 카드가 홍보물 역할 |
| Foundation Models 사용 | 특별 entitlement 불필요. ad-hoc 서명 앱에서도 동작 여부는 실기기 검증 필요 | 리스크 12장에 기록 |

### 10.2 릴리즈 절차

1. `main` 브랜치에 태그 `vX.Y.Z` 푸시
2. GitHub Actions(macOS 러너, 무료 티어)가 Release 빌드 → ad-hoc 서명 → zip 압축 → SHA-256 계산
3. Sparkle `generate_appcast`로 appcast.xml 갱신, GitHub Pages에 커밋
4. GitHub Release 생성: zip, 체크섬, 릴리즈 노트(변경점 + 설치 안내 링크) 첨부
5. 첫 릴리즈는 수동으로 진행해 절차를 검증한 뒤 자동화

### 10.3 저장소 구성

- 라이선스: MIT (Stats의 SMC 코드를 참고할 경우 저작권 고지 유지)
- README: 앱이 답하는 질문 한 줄, 리포트 카드 예시 이미지, 설치 가이드(Gatekeeper 우회 스크린샷), 수집 항목 전체 목록, 삭제 방법
- 이슈 템플릿: 판정 오류 신고용(리포트 JSON 첨부 요청)
- 앱 카테고리 매핑 JSON(F-21)은 저장소에서 PR로 기여받는다

### 14.2 검토 의견: 수집

4.1절과 4.2절이 지정한 수집 방식 가운데, macOS가 실제로 제공하는 지표와 어긋나는 것들이다.

### 14.2a F-02: 메모리 압박 등급은 샘플마다 읽는다

- 원문: F-02는 압박 등급의 출처로 `dispatch_source` 메모리 압박 이벤트를 든다.
- 문제: 이 이벤트는 등급이 **바뀌는 순간에만** 알린다. 5초마다 "지금 등급"을 기록하는 샘플링에는 맞지 않고, 앱이 이벤트를 한 번 놓치면 현재 등급을 알 방법이 없다.
- 제안: 샘플마다 `sysctl kern.memorystatus_vm_pressure_level`을 읽는다. 값은 1(정상), 2(경고), 4(위험)이고, 7장의 0/1/2로 바꿔 저장한다. 이 기기에서 일반 권한으로 읽히는 것을 확인했다. `dispatch_source`는 등급이 바뀐 시각을 샘플 간격보다 정확하게 남기는 보조 수단으로 둔다.
- 상태: 채택 (2026-09-20). `sysctl` 폴링만 채택하고 `dispatch_source` 보조 수단은 두지 않는다. 판정은 샘플 시간 중 비율로 계산하므로 샘플 간격보다 정밀한 변경 시각을 쓸 곳이 없고, 7장에도 그 값을 담을 컬럼이 없다

### 14.2b F-05: macOS에는 I/O 대기 지표가 없다

- 원문: F-05와 5장 디스크 행은 "I/O 대기 비율"을 쓴다.
- 문제: I/O 대기(iowait)는 Linux 커널이 CPU 시간을 나누는 항목이다. macOS의 `host_processor_info`는 user, system, idle, nice 네 가지만 준다. 원문대로 구현하면 이 지표는 항상 결측이다.
- 제안: `IOBlockStorageDriver`의 `Statistics`가 주는 누적값 `Total Time (Read)`, `Total Time (Write)`, `Latency Time`을 쓴다. 구간 증가량을 샘플 간격으로 나눠 "디스크가 요청을 처리하느라 바빴던 시간 비율"로 새로 정의한다. 요청이 겹치면 1을 넘을 수 있으므로 상한을 둔다. 이 기기에서 해당 키가 공개 IOKit으로 읽히는 것을 확인했다. 5장 디스크 행의 신호 정의와 7장 `io_wait` 컬럼의 뜻을 함께 고친다.
- 상태: 결정 대기

### 14.2c F-06: 스로틀링은 주파수와 온도만으로 판단할 수 없다

- 원문: F-06은 스로틀링 상태를 수집하고, 5장 열 행은 스로틀링을 "주파수가 정격 대비 20% 이상 하락 & 온도 상승"으로 정의한다.
- 문제: Apple Silicon은 스로틀링 여부를 알려 주는 값을 따로 제공하지 않는다. CPU 주파수는 부하가 줄 때와 작업이 E코어로 옮겨 갈 때도 정상적으로 내려가므로, 주파수와 온도만으로는 열 때문에 느려진 것인지 할 일이 줄어든 것인지 구별할 수 없다.
- 제안: 공개 API `ProcessInfo.thermalState`(nominal, fair, serious, critical)를 1차 신호로 쓰고, `serious` 이상이 된 구간 하나를 스로틀링 한 번으로 센다. IOReport 주파수는 "P코어 사용률이 높은데 주파수가 떨어졌다"는 보조 증거로만 쓴다. Apple Silicon의 온도는 비공개 `IOHIDEventSystemClient`를 거쳐야 하므로 IOReport와 같은 결측 허용 대상으로 둔다.
- 상태: 결정 대기

### 14.2d F-09, F-23: 다른 계정 소유 프로세스의 사용량은 일반 권한으로 못 읽을 수 있다

- 원문: F-09는 샘플마다 상위 프로세스 5개를 수집하고, F-23은 인덱싱·백업 같은 백그라운드 부하를 따로 표시한다. 8장은 관리자 권한(root helper)을 요구하지 않는다.
- 문제: `ps`와 `top`이 모든 프로세스의 사용량을 보여 주는 것은 두 도구가 setuid root로 설치되어 있기 때문이다(이 기기에서 권한 비트를 확인했다). 일반 권한 앱이 `proc_pid_rusage`로 다른 계정 소유 프로세스를 읽으면 거부될 가능성이 크다. 그런데 Spotlight 인덱싱의 `mds`와 Time Machine의 `backupd`는 root 소유이고 `mds_stores`는 `_mds_stores` 계정 소유다(이 기기에서 확인했다). F-23이 따로 보여 주려는 바로 그 부하가 빈칸으로 남을 수 있다.
- 제안: 0단계 검증 항목에 추가한다. 거부된다면 전체 CPU 사용률에서 읽을 수 있는 프로세스의 합을 뺀 나머지를 `시스템 프로세스(개별 측정 불가)`로 표시한다. `ps`를 5초마다 실행하는 방식은 프로세스 생성 비용이 F-10 예산을 잠식하므로 쓰지 않는다.
- 상태: 결정 대기

### 14.2e F-04: GPU 통계는 상위 클래스 IOAccelerator로 찾는다

- 원문: F-04는 IOKit `AGXAccelerator` 통계를 든다.
- 문제: 실제 클래스 이름은 칩 세대마다 달라진다. 이 기기(M5)에서는 `AGXAcceleratorG17G`였다. 이름을 고정하면 새 칩이 나올 때마다 결측이 된다.
- 제안: 상위 클래스 `IOAccelerator`로 매칭하고, `PerformanceStatistics`의 `Device Utilization %`와 `In use system memory`를 읽는다. 이 기기에서 공개 IOKit으로 두 값이 읽히는 것을 확인했다.
- 상태: 결정 대기

### 14.2f F-23: 자리를 비운 채 돌리는 작업을 판정에서 빼지 않는다

- 원문: F-23은 입력이 5분 이상 없거나 화면이 잠긴 시간을 판정 모수에서 뺀다.
- 문제: 영상 내보내기, 3D 렌더링, 긴 빌드는 걸어 두고 자리를 비우는 경우가 많다. 원문대로면 부하가 가장 큰 시간이 판정에서 빠지고, 실제로는 한계에 닿은 기기를 "여유"로 판정할 수 있다.
- 제안: 입력이 없어도 CPU나 GPU 사용률이 높으면 유휴가 아니라 `무인 작업`으로 분류해 모수에 넣는다. 사용률 기준은 `rules.json`에 둔다.
- 상태: 채택 (2026-09-20). 기준의 초기값은 CPU 전체 사용률 또는 GPU 사용률 50% 이상이다. Spotlight 인덱싱 같은 배경 작업은 대개 이보다 낮아 걸러지고, 빌드와 렌더링은 모수에 남는다

### 14.3 검토 의견: 판정 기준

5장 판정 기준과 13장 완료 기준에 대한 의견이다.

### 14.3a 5장 메모리 신호: 스왑 사용량 대신 스왑 증가량을 본다

- 원문: 메모리 한계 신호에 "스왑 사용량 > 1GB"가 들어 있다.
- 문제: 스왑으로 내보낸 페이지는 압박이 풀린 뒤에도 다시 읽히거나 프로세스가 끝날 때까지 스왑에 남는다. 오전에 스왑이 한 번 1GB를 넘으면 그날 내내 한계 신호가 켜진 것으로 계산되어 비율이 부풀려진다.
- 제안: 누적값 `swap_out`의 구간 증가량이 기준을 넘은 샘플만 신호로 센다. 스왑 사용량 자체는 근거 수치로 리포트에 남긴다.
- 상태: 채택 (2026-09-20). 기준의 초기값은 초당 1MB다. 샘플 구간의 증가량을 실제 경과 시간으로 나눈 비율로 비교하므로, 1초 세션과 5초 샘플에 같은 기준이 적용되고 잠자기 공백 구간은 신호가 되지 않는다. 7일 검진 뒤 보정한다

### 14.3b 5장 보조 규칙: 의도된 풀부하를 포그라운드 앱만으로 판별하지 않는다

- 원문: 워크로드가 "렌더링·컴파일·내보내기처럼 본래 풀부하를 쓰는 작업이면" CPU 등급을 한 단계 낮춘다.
- 문제: 워크로드는 포그라운드 앱으로 분류한다(F-08, F-20). 빌드를 걸어 두고 브라우저를 보면 포그라운드는 `브라우징·문서`라서 의도된 풀부하로 인정되지 않는다. 반대로 IDE를 띄워 둔 채 무관한 프로세스가 CPU를 잡아도 인정된다.
- 제안: 포그라운드 카테고리와 함께 그 샘플의 상위 프로세스(F-09)도 본다. `swift-frontend`, `clang`, `ffmpeg`처럼 풀부하가 정상인 프로세스 이름 목록을 `app-categories.json`에 함께 둔다.
- 상태: 결정 대기

### 14.3c 5장 열 행: 횟수 기준을 활성 시간으로 정규화한다

- 원문: 열 등급은 "주 1\~3회", "주 4회 이상"으로 정한다.
- 문제: 검진 기간은 7/14/30일 중에서 고르고(F-01), 하루에 맥을 쓰는 시간도 사람마다 다르다. 달력 주로 나누면 적게 쓴 사람일수록 유리하게 판정된다.
- 제안: 활성 시간 일정량을 한 주로 보고(예: 활성 40시간당 횟수) 분모를 활성 시간으로 둔다. 기준 시간은 `rules.json`에 둔다.
- 상태: 결정 대기

### 14.3d 13장: 검증할 수 있는 수용 기준이 없다

- 원문: 13장의 완료 기준은 "리포트가 나오고", "표시됨" 같은 정성적 문장이다.
- 문제: 판정 오류는 이 앱이 신뢰를 잃는 가장 큰 경로다(12장). 무엇이 통과인지 정해져 있지 않으면, 5장 임계값을 고칠 때 이전 판정이 뒤집히는 회귀를 알아챌 방법이 없다.
- 제안: 1단계를 시작하기 전에 고정 샘플 픽스처와 기대 판정을 짝지은 수용 기준을 정의한다. 예를 들어 "메모리 압박 경고가 활성 시간의 21%인 14일 픽스처는 메모리 한계로 판정한다"처럼 적는다. 식별자 계열을 새로 만들면 `scripts/kb.swift`의 `SYM_PREFIXES`에 더한다.
- 상태: 채택 (2026-09-20). 정의 시점은 1단계 시작 전이 아니라 메모리 판정을 구현하기 직전이다. 수용 기준이 지키는 대상은 판정이고, 그 앞의 수집·저장 작업은 판정을 건드리지 않는다. 식별자 계열(`AC-01` 형식)은 수용 기준 문서를 만들 때 `SYM_PREFIXES`에 더한다

### 14.4 검토 의견: 온디바이스 AI

6장과 4.4절에 대한 의견이다.

### 14.4a A-04: 수치는 모델이 아니라 앱이 넣는다

- 원문: A-04는 생성한 뒤에 입력 수치가 출력에 그대로 있는지 확인하고, 다르면 템플릿으로 대체한다.
- 문제: 이 검증은 두 방향으로 틀린다. 모델이 `23%`를 `23퍼센트`로, `1.5GB`를 `1,536MB`로 바꿔 쓰면 옳은 문장이 불일치로 버려진다. 반대로 입력에 없는 수치를 지어내 덧붙인 문장은 "입력 수치가 들어 있는가"만 보는 검사를 통과한다.
- 제안: 모델에게는 수치 대신 `{memory_limit_ratio}` 같은 자리표시자만 쓰게 하고, 앱이 결정론적으로 치환한다. 검증 조건은 "출력에 숫자가 하나도 없고, 자리표시자가 전부 입력에 있는 이름인가"로 바꾼다. 그러면 모델이 수치를 바꾸는 일이 구조적으로 불가능해진다.
- 상태: 결정 대기

### 14.4b F-41, A-06, A-07: 폴백을 사용자에게 드러낼지 정한다

- 원문: F-41은 AI를 쓸 수 없을 때 "사용자는 차이를 느끼지 않아야 한다"고 하고, A-06은 템플릿 리포트를 먼저 보여 준 뒤 AI 문장으로 채우며, A-07은 폴백 여부를 리포트 하단에 표기한다.
- 문제: 세 요구가 서로 어긋난다. A-06대로면 사용자가 보는 앞에서 문장이 바뀌고, A-07대로면 차이를 일부러 알린다.
- 제안: 하나로 정리한다. 권장안은 폴백을 숨기지 않고 알리는 것(A-07)이다. 근거 우선 원칙(2장)과 맞고, 판정 오류를 신고받았을 때 문장이 어느 경로로 만들어졌는지 알 수 있다. 그 경우 F-41은 "템플릿 문장도 같은 정보를 전달한다"로 고친다.
- 상태: 결정 대기

### 14.4c A-01: 한국어 지원 여부를 따로 확인한다

- 원문: A-01은 기기 미지원, Apple Intelligence 꺼짐, 모델 다운로드 중을 불가 사유로 든다.
- 문제: 리포트 문장은 한국어로만 만든다(F-64). 모델을 쓸 수 있어도 한국어를 지원하지 않으면 생성이 실패한다.
- 제안: `SystemLanguageModel.supportsLocale`로 한국어 지원을 확인하고, 불가 사유에 `한국어 미지원`을 더한다.
- 상태: 결정 대기. 뼈대의 `NarratorAvailability`에는 이 확인을 미리 넣어 두었다

### 14.5 검토 의견: 배포와 비기능

8장, 10장, 13장에 대한 의견이다.

### 14.5a F-11: ad-hoc 서명에서는 업데이트 뒤 로그인 항목이 풀릴 수 있다

- 원문: F-11은 `SMAppService.mainApp`으로 로그인 항목을 등록하고, 10.1절은 ad-hoc 서명으로 배포한다.
- 문제: `SMAppService` 등록은 앱의 코드 서명에 묶인다. ad-hoc 서명은 빌드할 때마다 달라지므로, 업데이트로 앱을 교체하면 자동 실행이 조용히 꺼질 수 있다. 같은 방식으로 배포하는 Moja의 개발 문서가 이 주의 사항을 적어 두었다. 검진 도중 이렇게 되면 재부팅 이후 데이터가 비고, 사용자는 리포트를 받을 때까지 그 사실을 모른다.
- 제안: 실행할 때마다 등록 상태를 확인하고, 풀려 있으면 메뉴에 알린다. Sparkle을 도입한 뒤에는(14.1) 검진이 진행 중일 때 업데이트 설치를 검진이 끝난 뒤로 미룬다.
- 상태: 방식을 바꿔 채택 (2026-09-20). 확인과 알림만으로는 원인이 남으므로, Moja가 쓰는 방식대로 배포본을 자체 서명 인증서(`JinMac Self-Signed`)로 서명한다. 그러면 지정 요구사항이 cdhash가 아니라 `identifier "dev.liampark.jinmac" and certificate leaf H"..."`로 잡혀 버전이 바뀌어도 그대로다. Moja는 2026-09-18에 설치본을 교체해도 로그인 항목 등록이 유지되는 것을 확인했고, `SMAppService`는 인증서의 루트가 신뢰되지 않아도 정상 동작했다. 실행할 때마다 등록 상태를 확인해 메뉴에 알리는 제안도 인증서 분실이나 ad-hoc 빌드 설치에 대비해 함께 둔다. 0단계의 Foundation Models 확인도 이 배포 서명으로 한다. 인증서는 Gatekeeper 경고를 없애지 못하고 Team ID도 없으므로 14.1의 Sparkle 보류 판단은 바뀌지 않는다. 검진 중 업데이트를 미루자는 제안은 Sparkle을 도입할 때 다시 본다

### 14.5b 8장: `top_process`까지 기록하면 디스크 쓰기 하루 5MB를 넘기기 쉽다

- 원문: 8장은 디스크 쓰기를 하루 5MB 미만으로 두고, 7장은 `sample`을 14일에 약 40MB로 추정하며 `top_process`를 샘플당 5행으로 둔다.
- 문제: `sample`만으로 하루 약 2.9MB다. `top_process`는 14일이면 약 121만 행이고, 행마다 타임스탬프·이름·수치 두 개와 색인이 붙으므로 하루 수 MB가 더해진다. WAL 체크포인트가 같은 페이지를 다시 쓰는 양도 쓰기에 포함된다.
- 제안: 상위 프로세스는 한계 신호가 켜진 샘플에서만 기록하거나 60초에 한 번으로 줄인다. 1단계에서 하루 쓰기량을 실측한 뒤 이 항목을 확정한다.
- 상태: 결정 대기

### 14.5c F-10, F-22: 1초 간격 세션이 자원 예산에 드는지 정한다

- 원문: F-10과 8장은 수집기 CPU 평균 1% 미만을 요구하고, F-22는 수동 세션을 1초 간격으로 기록한다.

- 제안: 세션 예산을 따로 적는다. 사용자가 무거운 작업을 재려고 켠 구간이므로, 측정 부하가 결과를 흐리지 않는 선을 0단계에서 실측으로 정한다.
- 상태: 결정 대기

### 14.5d 10.2절: Actions 무료 조건과 SDK 버전을 적는다

- 원문: 10.2절은 GitHub Actions macOS 러너를 무료 티어로 쓴다.
- 문제: macOS 러너를 추가 비용 없이 쓰려면 공개 저장소여야 한다. 또 Foundation Models를 컴파일하려면 macOS 26 이상 SDK가 든 Xcode가 러너 이미지에 있어야 한다.

### 14.5e 13장: 개발 단계와 버전 번호를 짝짓는다

- 원문: 13장은 각 단계가 GitHub Release 태그 하나로 끝난다고 하지만, 태그 번호는 정하지 않았다.
