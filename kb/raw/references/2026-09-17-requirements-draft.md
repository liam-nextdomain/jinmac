# 맥 작업 부하 검진 앱 개발 요구사항

2026-09-17 · @Someone

## 1. 개요와 목적

이 앱은 "지금 내가 하는 작업을 이 맥이 잘 소화하고 있는가"라는 질문에 측정 데이터로 답한다. 상시 모니터가 아니라 검진 도구다. 설치 후 1\~2주 동안 백그라운드에서 사용량을 기록하고, 기록이 끝나면 한국어 "작업 부하 프로파일 리포트"를 한 번 생성한다.

기존 모니터링 앱(iStat Menus, Stats, TG Pro)은 숫자를 보여주는 데서 끝나고, MacPulse는 스로틀링·배터리 같은 이벤트를 설명한다. 이 앱의 차별점은 사용자의 실제 워크로드와 기기의 궁합을 자원별로 판정하고, 다음 기기 구매 결정에 쓸 수 있는 근거를 남기는 것이다.

리포트가 답하는 세 가지:

- 지난 기간 동안 어느 자원(RAM, CPU, GPU, 디스크, 열)이 얼마나 자주 한계에 닿았는가
- 그때 어떤 작업(포그라운드 앱)을 하고 있었는가
- 다음 맥을 산다면 어느 항목을 올리고 어느 항목은 유지해도 되는가

## 2. 핵심 원칙과 제약

운영 비용 0원, 데이터 외부 전송 0건, 애플 개발자 등록 없음이 설계 전체를 규정한다.

| 제약 | 요구사항 |
| --- | --- |
| 비용 | 서버, 클라우드 API, 유료 SDK, 유료 인증서를 일절 쓰지 않는다. Apple Developer Program($99/년)도 가입하지 않는다. |
| 로컬 전용 | 수집·저장·분석·리포트 생성이 모두 사용자 기기 안에서 끝난다. 앱은 네트워크 요청을 하지 않는다(업데이트 확인 제외). |
| 해석 | 판정은 결정론적 규칙 엔진이 내리고, 온디바이스 AI는 판정 결과를 한국어 문장으로 다듬는 데만 쓴다. AI가 판정을 바꾸거나 수치를 만들어내지 않는다. |
| 배포 | GitHub Releases로 직배포. App Store, 공증(notarization), Developer ID 서명 없음. |
| 수익 | 무료. 광고, 인앱 결제, 텔레메트리 없음. |
| 근거 우선 | 모든 판정 문장은 근거 수치(발생 시간 비율, 발생 횟수, 당시 앱)를 함께 표시한다. 근거 없는 권고는 출력하지 않는다. |

## 3. 대상 사용자와 사용 시나리오

1차 사용자는 다음 맥 구매를 앞두고 "지금 기기로 충분한가, 어디를 올려야 하나"를 고민하는 맥 사용자다. 커뮤니티에서 "이 작업에 이 스펙이면 되나요"라고 묻는 사람이 바로 이 사용자다.

| 시나리오 | 사용자 행동 | 앱이 하는 일 |
| --- | --- | --- |
| 구매 전 검진 | 설치 후 평소처럼 1\~2주 사용 | 백그라운드 기록 → 종료 시 리포트 생성 |
| 특정 작업 점검 | 영상 편집·빌드 같은 작업 전에 "세션 시작" 클릭, 끝나면 "세션 종료" | 그 구간만 1초 간격 고해상도 기록 → 세션 리포트 |
| 커뮤니티 공유 | 리포트 카드(PNG)를 내보내 게시글에 첨부 | 표준 형식 카드 + JSON 생성 |
| 재검진 | 새 맥으로 바꾼 뒤 같은 기간 다시 기록 | 이전 리포트와 비교 |

사용자는 기술 용어를 몰라도 리포트를 읽을 수 있어야 한다. "메모리 압박", "스왑" 같은 용어는 리포트 안에서 한 줄 설명과 함께 쓴다.

## 4. 기능 요구사항

기능은 수집 → 태깅 → 판정 → 리포트 → 내보내기의 다섯 단계로 나뉜다. 각 항목 앞의 코드(F-xx)는 이슈 추적용 식별자다.

### 4.1 수집 (Collector)

| 코드 | 요구사항 | 비고 |
| --- | --- | --- |
| F-01 | 기본 5초 간격(설정 가능 1\~30초)으로 아래 지표를 샘플링한다 | 검진 기간 기본 14일, 사용자가 7/14/30일 중 선택 |
| F-02 | 메모리: 총량, 사용량, 압축 메모리, 스왑 사용량, 스왑 in/out 누적, macOS 메모리 압박 등급(정상/경고/위험) | `host_statistics64`, `sysctl vm.swapusage`, `dispatch_source` 메모리 압박 이벤트 |
| F-03 | CPU: 전체 사용률, P코어/E코어 별 사용률, 현재 주파수 | `host_processor_info`, IOReport(주파수) |
| F-04 | GPU: 사용률, 사용 메모리 | IOKit `AGXAccelerator` 통계 |
| F-05 | 디스크: 읽기/쓰기 처리량, I/O 대기 비율, 남은 용량 비율 | IOKit 블록 스토리지 통계 |
| F-06 | 열: CPU/GPU 온도, 팬 RPM, 스로틀링 상태 | SMC(IOHIDFamily on Apple Silicon). 읽기 실패 시 항목 비활성화하고 계속 진행 |
| F-07 | 전력: 배터리 여부, 전원 연결 여부 | 배터리 모드 여부는 판정 가중치에 반영 |
| F-08 | 컨텍스트: 매 샘플마다 포그라운드 앱 번들 ID, 화면 잠금/유휴 여부 | `NSWorkspace.frontmostApplication`, `CGEventSource` 유휴 시간 |
| F-09 | 샘플마다 상위 CPU/메모리 프로세스 5개의 이름과 사용량 | 사용자 데이터(파일명, 창 제목)는 수집하지 않는다 |
| F-10 | 수집기 자체 CPU 사용률 평균 1% 미만, 상주 메모리 50MB 미만 | 측정 도구가 부하를 만들지 않아야 한다 |
| F-11 | 잠자기·재부팅 후 자동 재개. 로그인 항목 등록은 사용자 동의 후 | `SMAppService.mainApp` |

## 5. 규칙 엔진 판정 기준 (초안)

판정 모수는 유휴를 뺀 활성 시간이며, 각 자원은 "한계 신호가 활성 시간 중 차지한 비율"로 등급을 정한다. 아래 임계값은 초기값이고, 번들 JSON(F-32)에서 조정한다.

| 자원 | 한계 신호 정의 | 여유 | 경계 | 한계 |
| --- | --- | --- | --- | --- |
| 메모리 | 메모리 압박 "경고" 이상, 또는 스왑 사용량 > 1GB | < 5% | 5\~20% | > 20% |
| 메모리(강) | 메모리 압박 "위험" | 0% | < 2% | ≥ 2% |
| CPU | P코어 평균 사용률 ≥ 90%가 30초 이상 지속 | < 10% | 10\~30% | > 30% |
| GPU | GPU 사용률 ≥ 90%가 30초 이상 지속 | < 10% | 10\~30% | > 30% |
| 열 | 스로틀링(주파수가 정격 대비 20% 이상 하락 & 온도 상승) | 0회 | 주 1\~3회 | 주 4회 이상 또는 1회 10분 이상 |
| 디스크 | I/O 대기 ≥ 30%가 30초 이상, 또는 남은 용량 < 15% | < 5% | 5\~15% | > 15% 또는 용량 부족 |

판정 보조 규칙:

- CPU가 "한계"라도 그때 워크로드가 렌더링·컴파일·내보내기처럼 본래 풀부하를 쓰는 작업이면 "의도된 풀부하"로 표기하고 등급을 한 단계 낮춘다. 풀부하 자체는 병목이 아니라 정상 동작이다.
- 메모리 "한계"와 디스크 I/O 대기가 같은 시간대에 겹치면 "스왑으로 인한 디스크 부하"로 묶어 메모리 항목으로 귀속시킨다.
- 배터리 모드에서만 발생한 CPU·열 신호는 별도 표기하고 전원 연결 시 데이터로 다시 판정한다.
- 강한 메모리 신호("메모리(강)")가 한계면 다른 항목과 무관하게 종합 판정을 "한계"로 둔다. RAM은 Apple Silicon에서 구매 후 늘릴 수 없는 유일한 자원이라 가장 보수적으로 본다.
- 종합 판정은 자원별 등급 중 가장 나쁜 것을 따르되, 근거 문장에는 어느 자원 때문인지 명시한다.

구매 참고 매핑(F-42):

| 판정 | 구매 참고 문구(요지) |
| --- | --- |
| 메모리 한계 | 다음 기기에서 RAM 한 단계 상향을 최우선으로 |
| 메모리 경계 | 현재 용량은 가능하나 작업이 늘 예정이면 상향 고려 |
| CPU 한계 (의도된 풀부하 아님) | 코어 수가 많은 칩 등급 상향 |
| CPU 한계 (의도된 풀부하) | 칩 상향 시 해당 작업 시간이 줄어들지만 필수는 아님 |
| GPU 한계 | GPU 코어 수가 많은 칩 등급 상향 |
| 열 한계 | 팬이 있는 폼팩터(MacBook Pro, Mac mini, Mac Studio) 고려 |
| 디스크 용량 부족 | 저장 용량 상향 또는 외장 SSD |

## 6. 온디바이스 AI 요구사항

AI는 Apple의 Foundation Models 프레임워크(macOS 26 이상, Apple Intelligence 활성화 필요)를 쓰고, 역할은 규칙 엔진 결과를 한국어 문장으로 다듬는 것으로 제한한다.

| 코드 | 요구사항 |
| --- | --- |
| A-01 | `SystemLanguageModel.default.availability`로 사용 가능 여부를 확인하고, 불가 사유(기기 미지원, Apple Intelligence 꺼짐, 모델 다운로드 중)를 설정 화면에 표시한다 |
| A-02 | 입력은 규칙 엔진의 구조화 결과(자원별 등급, 근거 수치, 상위 워크로드·프로세스)만 넘긴다. 원시 샘플, 프로세스 전체 목록, 파일 경로는 넘기지 않는다 |
| A-03 | 출력은 `@Generable` 구조체로 받는다: 요약(3문장 이내), 자원별 설명(각 2문장 이내), 구매 참고 문장. 자유 텍스트를 그대로 리포트에 쓰지 않는다 |
| A-04 | 프롬프트에 등급과 수치를 바꾸지 말라는 지시를 넣고, 생성 후 검증 단계에서 입력 수치가 출력에 그대로 있는지 확인한다. 불일치 시 템플릿 문장으로 대체 |
| A-05 | 컨텍스트 한계(약 4천 토큰)를 고려해 자원 항목별로 나눠 호출한다. 리포트 1건당 호출 6회 이내 |
| A-06 | 생성 시간 목표 10초 이내(M1 기준). 초과 시 템플릿 리포트를 먼저 보여주고 AI 문장을 나중에 채운다 |
| A-07 | Foundation Models 불가 시 폴백은 템플릿 문장이다. 폴백 여부는 리포트 하단에 한 줄로 표기한다 |
| A-08 | llama.cpp·MLX 등 모델 내장 방식은 채택하지 않는다. 앱 용량과 발열 때문에 "측정 도구가 부하를 만드는" 문제가 생긴다 |
| A-09 | 사용자 본인 API 키 입력 기능은 1차 범위에서 제외한다(비용·네트워크 0 원칙 유지) |

프롬프트 설계 원칙: 문체는 존댓말 설명문, 단정 대신 근거 인용("\~한 시간이 전체의 23%였습니다"), 과장 어휘 금지, 모델명·가격 언급 금지.

## 7. 데이터 모델과 저장

모든 데이터는 `~/Library/Application Support/<앱이름>/` 아래 SQLite 파일 하나에 저장하고, 앱 삭제 안내에 이 경로를 명시한다.

| 테이블 | 주요 컬럼 | 비고 |
| --- | --- | --- |
| `sample` | ts, mem\_used, mem\_compressed, swap\_used, swap\_in, swap\_out, mem\_pressure(0/1/2), cpu\_total, cpu\_p, cpu\_e, cpu\_freq, gpu\_util, gpu\_mem, disk\_read, disk\_write, io\_wait, temp\_cpu, temp\_gpu, fan\_rpm, throttled(bool), on\_battery(bool), idle(bool), front\_app | 5초 간격, 14일 ≈ 24만 행, 약 40MB |
| `top_process` | sample\_ts, name, cpu, mem | 샘플당 5행 |
| `session` | id, name, started\_at, ended\_at, interval\_sec | 수동 세션 메타 |
| `session_sample` | session\_id + `sample`과 동일 컬럼 | 1초 간격 |
| `checkup` | id, started\_at, ended\_at, target\_days, status | 검진 1회 = 1행 |
| `report` | id, checkup\_id, created\_at, verdict\_json, text\_json, schema\_version | 판정 결과와 문장을 분리 저장 |
| `app_category` | bundle\_id, category, user\_overridden | 내장 매핑 + 사용자 수정 |

- 검진 종료 후 원시 `sample`은 리포트 생성이 끝나면 요약(시간별 집계)으로 축약하고 원본은 30일 뒤 삭제한다. 사용자가 CSV로 보관할 수 있다.
- 리포트 JSON 스키마는 `schema_version`을 두어 비교 기능(F-52)에서 호환성을 검사한다.
- 저장 파일은 암호화하지 않는다(외부 전송이 없고, 내용에 사용자 파일 정보가 없음).

| 접근성 | VoiceOver로 리포트 본문을 읽을 수 있어야 한다. 등급은 색만이 아니라 텍스트로도 표시 |
| 보안 | 관리자 권한(root helper) 요구하지 않는다. 팬 제어 등 쓰기 동작 없음 |
| 언어 | UI·리포트 한국어 우선. 영어 UI 리소스는 준비하되 리포트 문장 생성은 1차 한국어만 |

## 9. 기술 스택

전부 Apple 기본 프레임워크와 무료 오픈소스로 구성하고, 유료·서버 의존 라이브러리는 쓰지 않는다.

| 영역 | 선택 | 이유 |
| --- | --- | --- |
| 언어·UI | Swift 6, SwiftUI, AppKit(메뉴바 `NSStatusItem`) | 네이티브, 추가 비용 없음 |
| 수집 | Mach/BSD API(`host_statistics64`, `sysctl`), IOKit, IOReport(private, 주파수·전력) | 샌드박스 없이 접근 가능. IOReport는 비공개 API라 OS 업데이트 시 깨질 수 있어 결측 허용 설계 |
| 온도·팬 | SMC 읽기(오픈소스 Stats 앱의 SMC 코드 참고, MIT) | Apple Silicon은 IOHIDFamily 경유 |
| 저장 | SQLite(GRDB.swift, MIT) | 경량, 집계 쿼리 편리 |
| 차트 | Swift Charts | 리포트·PDF 렌더링 공용 |
| 리포트 렌더 | SwiftUI `ImageRenderer`(PNG 카드), `NSPrintOperation` 또는 ImageRenderer(PDF) | 외부 라이브러리 불필요 |
| AI | Foundation Models 프레임워크 | 6장 참조 |
| 자동 시작 | `SMAppService` | 로그인 항목, 사용자 동의 필요 |
| 업데이트 | Sparkle 2(MIT), EdDSA 키는 자체 생성, appcast는 GitHub Pages 호스팅 | 개발자 등록 불필요 |
| 빌드·배포 | Xcode, GitHub Actions(무료 티어)로 릴리즈 zip 생성 | 10장 참조 |
| 테스트 | XCTest, 규칙 엔진용 고정 샘플 픽스처 | 결정론 검증 |

## 10. 배포

GitHub Releases로 zip을 직배포하되, 개발자 등록이 없으므로 Gatekeeper 경고를 사용자가 스스로 넘기게 안내하는 것이 배포의 핵심 과제다.

### 10.1 개발자 미등록이 만드는 제약

| 제약 | 영향 | 대응 |
| --- | --- | --- |
| Developer ID 서명·공증 불가 | 처음 실행 시 "확인되지 않은 개발자" 경고. macOS 15부터는 우클릭 → 열기 우회가 사라져 시스템 설정 → 개인정보 보호 및 보안 → "그래도 열기"를 눌러야 한다 | README와 릴리즈 노트에 스크린샷 포함 설치 가이드. 터미널 대안 `xattr -d com.apple.quarantine <앱경로>`도 함께 안내 |
| 서명 없음 = 앱 무결성 보장 없음 | 배포 파일 변조 여부를 사용자가 확인할 수 없음 | 릴리즈마다 SHA-256 체크섬 게시. ad-hoc 서명(`codesign -s -`)은 반드시 적용(미서명 바이너리는 Apple Silicon에서 실행 자체가 거부됨) |
| iCloud, 푸시, App Groups 등 유료 계정 전용 기능 불가 | 이 앱은 해당 기능을 쓰지 않음 | 영향 없음 |
| App Store 배포 불가 | 검색 노출 없음 | 커뮤니티(맥쓰사 등)와 GitHub가 유일한 유통 경로. 리포트 카드가 홍보물 역할 |
| Foundation Models 사용 | 특별 entitlement 불필요. ad-hoc 서명 앱에서도 동작 여부는 실기기 검증 필요 | 리스크 12장에 기록 |

### 10.2 릴리즈 절차

1. `main` 브랜치에 태그 `vX.Y.Z` 푸시
2. GitHub Actions(macOS 러너, 무료 티어)가 Release 빌드 → ad-hoc 서명 → zip 압축 → SHA-256 계산
3. Sparkle `generate_appcast`로 appcast.xml 갱신, GitHub Pages에 커밋
4. GitHub Release 생성: zip, 체크섬, 릴리즈 노트(변경점 + 설치 안내 링크) 첨부
5. 첫 릴리즈는 수동으로 진행해 절차를 검증한 뒤 자동화

### 10.3 저장소 구성

- 라이선스: MIT (Stats의 SMC 코드를 참고할 경우 저작권 고지 유지)
- README: 앱이 답하는 질문 한 줄, 리포트 카드 예시 이미지, 설치 가이드(Gatekeeper 우회 스크린샷), 수집 항목 전체 목록, 삭제 방법
- 이슈 템플릿: 판정 오류 신고용(리포트 JSON 첨부 요청)
- 앱 카테고리 매핑 JSON(F-21)은 저장소에서 PR로 기여받는다

- Windows·Linux 지원

## 12. 리스크와 미결 사항

가장 큰 리스크는 Gatekeeper 경고로 인한 설치 이탈과 판정 오류로 인한 신뢰 손실이다.

| 리스크 | 영향 | 완화 |
| --- | --- | --- |
| Gatekeeper 경고로 설치 포기 | 사용자 확보 실패 | 설치 가이드 품질에 투자. 커뮤니티에서 먼저 신뢰를 쌓고 배포 |
| ad-hoc 서명 앱에서 Foundation Models 동작 불가 가능성 | AI 문장 생성 전체 폴백 | 개발 초기에 실기기 검증. 불가 시 템플릿 리포트 품질을 높이는 쪽으로 자원 이동 |
| IOReport 등 비공개 API가 OS 업데이트로 깨짐 | 주파수·스로틀링 항목 결측 | 결측 허용 설계(F-06). 온도 기반 대체 판정 준비 |
| 임계값 오설정으로 오판 | "RAM 충분" 오답 → 구매 실패 | 초기에는 메모리 판정만 "한계" 등급 허용, 다른 자원은 "경계"까지만. 커뮤니티 피드백으로 임계값 보정 |
| 앱 카테고리 매핑 불완전 | 워크로드 분석 부정확 | 사용자 수정 허용(F-21), PR 기여 |
| 기존 앱(MacPulse 등)의 기능 추가 | 차별점 약화 | 한국어·커뮤니티·구매 판정 프레임에 집중. 기능 경쟁 안 함 |

미결 사항:

- [ ] Foundation Models가 ad-hoc 서명 앱에서 동작하는지 M1 이상 실기기에서 확인
- [ ] Apple Silicon 세대별(M1\~M5) 온도·주파수 센서 키 목록 확보
- [ ] 앱 이름과 리포트 카드 디자인
- [ ] 검진 기본 기간 7일 vs 14일 결정 (데이터 충분성 vs 사용자 인내)
- [ ] Intel 맥 지원 범위 결정 (지원 시 테스트 기기 필요)

## 13. 개발 단계

MVP는 메모리 판정 하나를 끝까지(수집 → 판정 → 한국어 리포트 → PNG 카드) 관통하는 것이다. 자원 종류를 늘리기보다 한 자원의 판정과 문장이 신뢰할 만한지 먼저 검증한다.

| 단계 | 범위 | 완료 기준 |
| --- | --- | --- |
| 0. 검증 | ad-hoc 서명 앱에서 Foundation Models 호출, SMC 온도 읽기, IOReport 주파수 읽기 | 세 항목의 가능/불가가 실기기에서 확인됨 |
| 1. MVP | 메뉴바 앱, 메모리·CPU 수집(F-02, F-03, F-08), SQLite 저장, 메모리 규칙 판정, 템플릿 한국어 리포트, PNG 카드, GitHub Release 수동 배포 | 본인 기기에서 7일 검진 후 리포트가 나오고, 커뮤니티에 카드를 올릴 수 있음 |
| 2. 해석 강화 | Foundation Models 문장 생성 + 검증(A-01\~A-07), 워크로드 태깅(F-20\~F-23), CPU·GPU·열 판정, 수동 세션 | 리포트에 "어떤 작업에서" 한계가 왔는지 표시됨 |
| 3. 공유·비교 | JSON 내보내기·불러오기·비교(F-52), PDF, Sparkle 자동 업데이트, Actions 릴리즈 자동화 | 새 기기 리포트와 이전 리포트를 나란히 비교 가능 |
| 4. 보정 | 커뮤니티 피드백으로 임계값·카테고리 매핑 조정, 판정 오류 이슈 처리 | 판정 오류 신고율 하락 |

각 단계는 GitHub Release 태그 하나로 끝나고, 다음 단계 시작 전에 커뮤니티에 한 번 공개해 반응을 본다.
